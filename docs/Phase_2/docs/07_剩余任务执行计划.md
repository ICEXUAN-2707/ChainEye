## 可直接创建的任务单

### G0：Phase 1收尾

1. `PR#8复现与合并`：另一开发者复现完成Run的报告加载、Claim四类引用、原件/计算入口、失败重试、Run切换隔离及Markdown/PDF下载；核对在线CI与所有未解决评论后合并。
2. `前端依赖安全维护`：从最新`main`建立独立`chore/frontend-vite-security`，将Vite锁定到修复版本，保留`package-lock.json`，运行`npm audit`、干净安装、测试与构建；不得使用`audit fix --force`绕过审查。
3. `Phase 1冻结`：在合并后的`main`执行AGENTS规定的全部命令，补可见浏览器和人工支持性记录，将`docs/Phase_1/README.md`改为`frozen`并记录唯一提交；从该提交创建一次`develop`。

### G1：P2.0现状与选型

1. `chore/p2-audit-contract`（Codex）：按implemented/partial/stub/missing核查上传、提取、复核、情景、Run、报告、迁移和错误语义；填写current-state与contract-delta，不新建平行DTO。
2. `chore/p2-ui-audit`（Claude）：核查数据包、复核、情景、Run、报告的加载/空/失败/partial/stale/窄屏状态，列出需要的真实接口和联调样例。
3. `spike/p2-ocr-selection`（Codex）：固定两种OCR候选版本，对同一20页且不少于60字段样本运行；记录许可证、安装、正确数/分母、覆盖率、表格列错、p50/p95、峰值内存和失败，形成ADR。
4. `data/p2-second-company`（共同）：从官方来源选择第二家电池企业，保存原件、发布日期与SHA256；适配材料和未见材料分离。选择结果及金融可比口径须人工确认。
5. `P2契约增量PR`（共同评审，Codex生成）：只在上述核查后更新后端权威模型、OpenAPI/Schema、生成TypeScript、接口文档和测试，再由双方各自建立功能分支。

### G2—G5：实现包

- P2.1先实现“上传→企业候选→人工确认→新版Dataset→第二企业原生PDF事实”的最小纵向流程，再扩展能力矩阵；不以字符串替换公司名复用CATL结果。
- P2.2先实现“解析作业→单页路线与警告→候选事实→原页/bbox→人工复核”的最小纵向流程；OCR不可用时保留可重试的明确降级。
- P2.3按M1盈利增长、M2现金营运、M5产业链情景优先，随后M3扩张资金、M4行业竞争；每个模块先定义输入事实、口径、计算、能力状态和拒绝条件，再接模型叙述与建议。
- P2.4冻结评测集和提示/配置hash，完成三次真实模型运行、单次提示对照、两机干净安装、未见材料、备份恢复、断网回放、JSON/Markdown/PDF一致性与可见页面检查。

## 全程约束与已知风险

- 每个契约变更先写原因、兼容和迁移，再从后端单一来源生成；金额继续使用人民币元十进制字符串，`ratio`展示乘100，`pp`不再乘100。
- Dataset、Run、解析配置和计算均绑定显式版本；事实更正新建revision，旧快照不静默覆盖；缺失保持`null + missing_reason`。
- CI不下载大型权重、不调用付费模型；真实OCR和DeepSeek检查在受控集成任务中执行并保存费用/失败，不能用mock宣称完成。
- 第二企业数据可得性、扫描质量、OCR许可证/模型体积、DeepSeek稳定性、两台机器资源预算仍是P2.0实测项，不预先写成结论。
- 团队财务签核、另一开发者复现、可见浏览器检查和PR互审只能由实际执行者确认。
