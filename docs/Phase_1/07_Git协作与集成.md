# Git 协作与集成

## 分支策略

`main` 是稳定集成分支，任何时刻都应通过后端测试、基线校验、契约漂移检查和前端构建。开发者先同步最新 `main`，再为单一任务创建短期分支：后端使用 `feat/rN-*-backend`，前端使用 `feat/rN-*-frontend`，修复使用 `fix/*`。一个分支只承载同一轮次、同一纵向流程，不夹带后续 R3—R6 功能。

功能不得直接提交到 `main`。短期分支通过 PR 合并，合并后删除；发布版本从已验收的 `main` 打标签。禁止改写共享分支历史或用强制推送覆盖他人提交。

## 目录责任与冲突处理

Codex 维护后端、迁移、后端测试及最终集成；Claude 维护前端页面、组件、样式和交互。契约、文档、验收记录和 CI 是共享区域。若一项改动跨越责任边界，PR 先写清用户流程、请求、响应与失败状态，再由各自负责人修改自己的目录。

发生冲突时以领域与 HTTP 模型为契约来源，不以某一端的临时实现为准。不得删除金额、单位、期间、证据、版本或错误字段来绕过集成问题。

## 契约同步

权威来源依次为后端路由、HTTP DTO 和领域模型。`contracts/openapi.json`、`contracts/*.schema.json` 与 `frontend/src/api/generated.ts` 是生成物。契约改动必须在同一 PR 中：

1. 说明变更原因、兼容性和受影响流程。
2. 更新权威模型、接口语义与契约测试。
3. 运行 `tools/export_contracts.py` 和 `tools/generate_ts.py`。
4. 提交全部生成物，并通知前端负责人基于新类型构建。

无意修改契约时，生成后 `git diff --exit-code -- contracts frontend/src/api/generated.ts` 必须通过。金额始终使用人民币元十进制字符串；Dataset 版本和 Fact revision 不得被省略或就地覆盖。

## PR 互审与合并门槛

每个 PR 至少由另一名开发者审阅。描述必须包含：新增行为、文件范围、接口变化、测试命令与真实结果、已知限制、人工待办、回滚方式和前后端联调示例。审阅者至少独立执行一个“输入→API→持久化/页面→来源”的关键流程。

合并前必须通过 GitHub Actions。涉及原件、金额或事实时，还需人工核对哈希、页码、单位、期间和口径；自动化测试不能替代财务签核。失败检查只能修复后重跑，不得修改金标准、跳过断言或伪造日志来获得绿色状态。

## 干净环境验收

从新克隆目录安装锁定依赖，且不复用 `.runtime/`、虚拟环境、`node_modules/` 或构建目录。依次执行后端测试、基线校验、契约生成和漂移检查、`npm ci`、前端构建及真实 HTTP 联调。CI 不注入 DeepSeek 密钥，不调用模型或其他付费服务。

验收记录必须注明操作系统、Python/Node 版本、测试数量、失败与修复、生成物是否漂移，以及没有执行的浏览器或实机步骤。
